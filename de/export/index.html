    Export: LaTeX-PDF des Lebenslaufs¶

    Für Fortgeschrittene (Operator-Inhalt)

    Diese Seite richtet sich an die Person, die den Export ausführt: Sie nennt Pakete, Kommandozeilen und einen Container. Willst du nur eine PDF eines geprüften Dokuments, bitte den Export-Skill darum (/claude-job-search:job-application-export) und komm hierher zurück, wenn er ein fehlendes Werkzeug meldet.

    Diese Seite beschreibt, was benötigt wird, um einen fertigen Lebenslauf mit dem LaTeX-Template in eine PDF umzuwandeln, und welche Befehle das ausführen. Einzige Eingabe ist die Markdown-Quelle. PDF und LaTeX-Quelle entstehen daraus.

    Welches Format für welchen Empfänger

    Eine Text-PDF ist der Standard, auch für Bewerbungsportale (ATS): Das Layout ist einspaltig ohne Tabellen, was Parser im Allgemeinen der Reihe nach lesen. Das ist eine Layout-Regel und eine Prüfung des ausgelesenen Textes (siehe „Was der Export prüft“), keine Aussage über ein bestimmtes ATS. DOCX erzeugst du nur, wenn ein Portal es ausdrücklich verlangt. HTML und Markdown dienen der Ansicht und deinen eigenen Unterlagen.

    Was benötigt wird¶

    Werkzeug Wofür Typisches Paket (Debian / Ubuntu)
    pandoc Markdown nach LaTeX, DOCX, HTML pandoc
    LuaLaTeX Kompilieren der PDF aus der LaTeX-Quelle texlive-luatex
    Deutsche Sprachunterstützung für LaTeX babel mit ngerman im Template texlive-lang-german
    Schriften für LuaLaTeX Das Template nutzt Lato und fällt ohne Lato auf Latin Modern Sans zurück fonts-lato, texlive-fonts-recommended
    poppler-utils pdfinfo und pdftotext für Seitenprüfung und Textprüfung poppler-utils
    python-docx Nur für DOCX, nicht für PDF pip install python-docx

    Die Tabelle nennt typische Paketnamen. Sie sind nicht auf jedem System geprüft. Das Ergebnis prüfst du mit pdfinfo und mit der Inhaltsprüfung des Exports.

    Für die LaTeX-Quelle allein (--format tex) reicht pandoc. LuaLaTeX ist dafür nicht nötig.

    Layout¶

    Die PDF ist einspaltig und nutzt eine Akzentfarbe (dunkles Blau), dünne Linien unter den Abschnittsüberschriften und farbige Aufzählungspunkte. Es gibt keine Tabellen, Symbole, Fotos oder Text in Kopf- und Fußzeile außer einer dezenten Seitenzahl, ein Parser liest also denselben Text wie die Markdown-Quelle.

    • Kopfbereich: Der Name steht zuerst und groß, darunter die persönlichen Angaben.
    • Stationen: Der Zeitraum steht in einer linken Spalte, die Position fett, Arbeitgeber und Ort darunter in Grau. Ausbildung und Zertifikate nutzen dieselbe Spalte für ihre Zeiträume.
    • Typografie: Lato in 10,5 pt auf 14,3 pt Zeilenabstand, Flattersatz, wenig Silbentrennung, Produktnamen wie VMware Tanzu brechen nicht um. Die Schrift wird nicht verkleinert, um zwei Seiten zu erreichen.
    • Druck und Bildschirm: Die Farben behalten ihren Kontrast auf Weiß (Text 15,8:1, Akzent 8,7:1, Grau 6,1:1), und die Hierarchie bleibt in Graustufen sichtbar.
    • Brief: Das Anschreiben nutzt dasselbe Template mit eigenen Rändern (25 mm links).

    Das Design steht in skills/job-application-export/templates/ (document.tex und cv.lua).

    Exit-Codes¶

    Code Bedeutung
    0 Export fertig
    1 Fehler, zum Beispiel email mit einem anderen Format als md
    2 Der Inhalt des Exports weicht von der Quelle ab; die Datei bleibt, ist aber nicht versandbereit
    3 --reproduce: abweichende Ausgabe oder geänderte Quelle
    4 Seitenlimit des Dokumenttyps überschritten; Datei und Manifest bleiben erhalten. Ein Lebenslauf mit format: einseitig hat das Limit einer Seite. Den Schweregrad setzt die Qualitätsprüfung

    Die Umgebungsvariablen PLUGIN_REVISION und EXPORT_IMAGE_ID stehen im Manifest unter umgebung.

    Für Entwickler

    Die Layoutregeln stehen in spec/job-application/lebenslauf/en.md (LB-11), die ATS-Regel in spec/job-application/konventionen/en.md (R-8.3, R-10).

    Eingabe¶

    Die Quelle ist eine Markdown-Datei eines Bewerbungsordners oder eines Ausprägungsordners:

    job-application/<slug>/lebenslauf.md                       der Lebenslauf einer Bewerbung
job-application/lebenslauf-basis/lebenslauf.md             der Arbeitsstand einer Ausprägung
job-application/lebenslauf-basis/versionen/v001_2026-10-22.md   eine eingefrorene Version dieser Ausprägung

    Der Export prüft die Seitenzahl gegen den Dokumenttyp. Ein Lebenslauf darf höchstens zwei Seiten haben.

    Eine eingefrorene Version exportieren. Die Kopie, die du versendest, sollte aus einer eingefrorenen Version stammen, nicht aus dem Arbeitsstand, damit sie sich später nachbauen lässt. Gib dem Export die Datei in versionen/; die Ausgabe landet in export/ desselben Ausprägungsordners und heißt nach der Version (v001_2026-10-22.pdf), nicht nach dem Tag des Exports. Für die Kopie an den Empfänger nutzt du --name Vorname_Nachname_Lebenslauf.

    Befehle¶

    Führe sie im Hauptverzeichnis des Plugin-Repositorys aus, dort liegt die Taskfile.yml:

    task export -- job-application/<slug>/lebenslauf.md --format pdf --doc-type cv
task export -- job-application/<slug>/lebenslauf.md --format pdf --doc-type cv --name Vorname_Nachname_Lebenslauf
task export -- job-application/<slug>/lebenslauf.md --format tex --doc-type cv
    Option Bedeutung
    --format pdf PDF, kompiliert mit LuaLaTeX
    --format tex Nur die LaTeX-Quelle, ohne Kompilieren
    --format docx Word-Dokument, braucht python-docx
    --format html oder md HTML- oder Markdown-Kopie
    --doc-type cv Lebenslauf, höchstens zwei Seiten
    --doc-type letter Anschreiben, eine Seite
    --doc-type motivation Motivationsschreiben, eine Seite für die Stellenvarianten, zwei Seiten bei studium und stipendium (Frontmatter-Schlüssel variante)
    --doc-type email E-Mail-Text, nur mit --format md
    --name Dateiname ohne Endung, Standard ist der Name der Quelle
    --out-dir Ausgabeordner, Standard export/ neben der Quelle: job-application/<slug>/export/ bei einer Bewerbung, job-application/<ausprägung>/export/ bei einer Ausprägung oder einer ihrer eingefrorenen Versionen

    Ergebnisse¶

    Im Ausgabeordner entstehen:

    • die PDF (<name>.pdf) und bei --format pdf die LaTeX-Quelle (<name>.tex). Die Hilfsdateien von LuaLaTeX werden gelöscht.
    • Seitenzahl und Ergebnis der Inhaltsprüfung auf der Konsole. Eine fehlgeschlagene Inhaltsprüfung wird gemeldet, und der Export gilt dann nicht als fertig.
    • ein Manifest (<name>.<ext>.manifest.json): Hash von Quelle, Vorlage und Ausgabe, Werkzeugversionen, das verwendete Datum und unter pruefung das Ergebnis der Prüfungen dieses Laufs (unten).

    Was der Export prüft¶

    Ein gelungener Export ist kein richtiger Lebenslauf und keine ATS-Garantie

    Die Prüfungen vergleichen die ausgegebene Datei mit ihrer Markdown-Quelle. Sie vergleichen sie nicht mit deiner Datengrundlage (das macht cv_checks.py im Quality Gate), und keine Prüfung bezieht ein Bewerbermanagementsystem ein. Ein Manifest entsteht auch bei einer fehlgeschlagenen Prüfung; es hält fest, was geprüft wurde, und bescheinigt den Lebenslauf nicht.

    Frage Prüfung Ergebnis
    Wurde die Datei erzeugt? Exit-Code der Werkzeuge, Datei geschrieben, Seitenzahl (pdfinfo) Fehler (Exit 1)
    Sind alle Wörter da und nur diese? Wortmenge der Quelle gegen den aus dem Export zurückgelesenen Text (Link-Ziele sind kein Text) Exit 2, Fehlend / Zusätzlich
    Sind Zahlen und Fakten intakt? Die Zeichen von Zahlen (% € $ + &) kommen gleich oft vor; jeder Stichpunkt steht mit denselben Wörtern in derselben Reihenfolge nach dem vorigen (von 800 ms auf 120 ms ist nicht von 120 ms auf 800 ms) Exit 2, Inhaltsabweichung
    Stehen die Abschnitte in Ordnung? Die Überschriften der Ebenen 1 und 2 folgen der Quelle (Heuristik) Warnung Reihenfolge, Exit-Code unverändert
    Hat die Datei die gewollte Struktur? DOCX und HTML: Überschriften je Ebene gegen die Quelle, Tabellen, Textfelder, Bilder, Text in Kopf- und Fußzeilen Warnung Struktur, Exit-Code unverändert
    Ist sie zu lang? Seitenlimit des Dokumenttyps (PDF) Exit 4
    Ist sie versandfertig? offene [ERGÄNZEN …] / [KLÄREN …] in der ganzen Datei Warnung, aufgelistet
    Ist ein zweiter Lauf gleich? --reproduce MANIFEST baut neu und vergleicht die Bytes Exit 3 bei Abweichung

    Zurückgelesen wird der reine Text der Datei: pdftotext bei der PDF, Absätze und Tabellenzellen bei DOCX, das HTML ohne Tags, der LaTeX-Rumpf bei tex. Markdown ist eine Kopie der Quelle und wird als nicht_geprueft vermerkt. Zeilen- und Seitenumbrüche, Trennstriche am Zeilenende, Aufzählungszeichen, die Seitenzahl und die Lage der Kopffelder gelten nicht als Abweichung.

    Was in diesem Repository getestet wird (tests/test_export.py, nur synthetische Daten) und was nicht:

    Aussage Grundlage
    Der Text der PDF lässt sich auslesen, die Stationszeile liest sich Zeitraum, Position, Arbeitgeber in dieser Reihenfolge, über mehrere Seiten geht keine Zahl und kein Zeichen verloren getestet mit pdftotext
    DOCX hat Word-Überschriftenformate in der Reihenfolge der Quelle, Aufzählungen, bei einem normalen Lebenslauf keine Tabelle; eine Tabelle oder ein Textfeld wird gemeldet getestet mit python-docx
    HTML hat lang="de", Überschriften und Listen der Quelle getestet
    Ein bestimmtes ATS liest die Datei richtig nicht getestet und nicht behauptet. Parser unterscheiden sich in Regeln und Formaten, und echte Bewerbungsdaten gehen an keinen externen Parser
    Der Text stimmt mit deiner Datengrundlage vom Export nicht geprüft (cv_checks.py, Reviewer)
    Das Layout sieht gut aus (Überlauf, hässlicher Seitenumbruch, Leerflächen) nicht automatisch geprüft; öffne die PDF

    Wo die Prüfungen laufen: Die Tests für DOCX, HTML, Markdown und tex laufen in der CI bei jedem Pull Request (pandoc und python-docx sind dort installiert). Die PDF-Tests brauchen LuaLaTeX und werden in der CI übersprungen. Sie laufen lokal oder im Export-Image (dessen pandoc ist älter; der Exporter fängt das ab):

    docker build -t claude-job-search-export .
docker run --rm --entrypoint sh -v "$PWD:/src:ro" claude-job-search-export \
  -c 'cp -r /src /tmp/w && cd /tmp/w && python3 -m unittest tests.test_export'

    Reproduzierbare PDFs¶

    Eine Quelle mit dem Frontmatter-Schlüssel version_datum (JJJJ-MM-TT) ist eine festgeschriebene Version. Der Export leitet dann Datum und PDF-ID der PDF aus der Quelle ab. Gleiche Quelle, gleiche Vorlage und gleiches Container-Image ergeben eine byte-identische PDF. Ohne version_datum trägt die PDF den Tag des Exports, und der Export gibt einen Hinweis aus.

    python3 skills/job-application-export/scripts/export_document.py --reproduce lebenslauf.pdf.manifest.json

    Der Befehl baut die Datei in einem temporären Ordner neu und vergleicht den Hash. Exit-Code 0 heißt identisch, 3 heißt abweichend oder geänderte Quelle; abweichende Werkzeugversionen werden aufgelistet. Bewahre das Container-Image einer versendeten PDF auf (docker save), weil sich die Debian-Pakete darin mit der Zeit ändern.

    Für Entwickler

    Ausprägungen, Versionen und Ordneraufbau stehen in spec/job-application/lebenslauf-versionen/en.md.

    Im Container ausführen, in einem anderen Repository¶

    Der Export läuft meist in dem Repository, das deine Bewerbungsdaten enthält, nicht im Plugin-Repository. Das Dockerfile enthält pandoc, LuaLaTeX, die deutsche Sprachunterstützung und poppler-utils, dort muss also nichts weiter installiert werden. Nötig ist nur Docker.

    Baue das Image einmal. Das Plugin-Repository ist die Build-Quelle, du musst es nicht klonen:

    docker build -t claude-job-search-export https://github.com/nolte/claude-job-search.git#develop

    Ersetze develop durch das Release-Tag, zum Beispiel v0.2.0, damit sich das Image nicht unter dir ändert.

    Starte es im Wurzelverzeichnis deines Daten-Repositories, dort liegt job-application/:

    docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" claude-job-search-export \
  job-application/<slug>/lebenslauf.md --format pdf --doc-type cv
    • --user "$(id -u):$(id -g)" sorgt dafür, dass die Dateien in export/ dir gehören. Das Image akzeptiert jede User-ID.
    • Das Ergebnis liegt in job-application/<slug>/export/ deines Repositories. Die Quelle wird nicht verändert.
    • --format tex, docx, html und md funktionieren genauso. --name Vorname_Nachname_Lebenslauf setzt den Dateinamen.
    • Starte den Befehl nach jeder Änderung am Lebenslauf neu. Eine alte PDF aktualisiert sich nicht von selbst.

    Mit Task im Daten-Repository verkürzt diese Taskfile.yml den Aufruf:

    version: '3'

vars:
  EXPORT_IMAGE: '{{.EXPORT_IMAGE | default "claude-job-search-export"}}'
  EXPORT_SOURCE: '{{.EXPORT_SOURCE | default "https://github.com/nolte/claude-job-search.git#develop"}}'
  APPLICATION_ROOT: '{{.APPLICATION_ROOT | default "job-application"}}'

tasks:
  export:image:
    desc: Build the export image from the plugin repository
    cmds:
      - docker build -t {{.EXPORT_IMAGE}} {{.EXPORT_SOURCE}}

  export:
    desc: "Export a document: task export SLUG=<vorgang> [DOC=lebenslauf] [FORMAT=pdf] [TYPE=cv]"
    requires:
      vars: [SLUG]
    vars:
      DOC: '{{.DOC | default "lebenslauf"}}'
      FORMAT: '{{.FORMAT | default "pdf"}}'
      TYPE: '{{.TYPE | default "cv"}}'
    cmds:
      - >-
        docker run --rm --user "$(id -u):$(id -g)" -v "$PWD:/work" {{.EXPORT_IMAGE}}
        {{.APPLICATION_ROOT}}/{{.SLUG}}/{{.DOC}}.md --format {{.FORMAT}} --doc-type {{.TYPE}}

    task export:image
task export SLUG=<slug>
task export SLUG=<slug> FORMAT=tex

    Prüfe das Ergebnis nach jedem Export: Die Konsole muss Inhaltsprüfung: ok ausgeben und keine Zeile Reihenfolge: Abweichung oder Struktur: … (ein Abschnitt steht anders als in der Quelle, oder die Datei enthält eine Tabelle oder ein Textfeld; Warnungen, der Exit-Code bleibt 0). Eine PDF mit nur wenigen Kilobyte und ohne Text ist ein fehlgeschlagener Export, auch wenn die Datei existiert. Nur der Export-Skill wird ins Image kopiert (.dockerignore), personenbezogene Daten deines Repositories gelangen also nie in den Build-Kontext.

    Was der Export nicht tut¶

    • Er ändert die Markdown-Quelle nie.
    • Er fügt keine personenbezogenen Daten oder Metadaten hinzu, außer dem grundlage_hash der Quelle.
    • Er versendet nichts. Der Versand ist ein eigener Schritt.
